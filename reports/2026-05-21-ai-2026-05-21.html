Harness 工程线：MCP Server redesign、AGENTS.md、Agent Loop 和 Knowledge Graph 指向 agent harness 实战

概述：这条真正有价值的点不是 Harness 又做了一个 MCP server，而是它给出了 agent harness 的工程约束：工具太多会吞上下文，LLM 不应该当 API 路由器。v2 从 130+ 工具压到 11 个，把 200K 上下文里的工具定义成本从约 26% 降到 1.6%，还用 registry dispatch 覆盖 125+ 资源类型。现在最值得借鉴的是架构模式，而不是直接采购 Harness；如果你在做内部 MCP server，这条可以马上转成工具预算和风险控制 checklist。

风险提示：Harness 本身是 DevOps 平台，内容天然带产品视角；可复用的是 MCP 架构和安全边界，不要把 Harness 平台能力等同于通用 agent harness。

推荐理由：它正好补上“harness engineering”视角：agent 不只是模型和框架，还要有工具协议、仓库约束、结构化数据和执行环境。

  • Harness Engineering Blog：安全控制包含 write confirmation、fail-closed deletes、read-only mode。
